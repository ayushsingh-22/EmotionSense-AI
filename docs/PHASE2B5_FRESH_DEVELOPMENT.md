## Local dry-run tooling

From `backend/`, the following command prints the reviewed child-first deletion plan but does
not connect to a database and does not execute SQL:

```powershell
node scripts/fresh-development-cleanup.mjs
```

The plan is generated by
`[freshDevelopmentGuard.mjs](../backend/scripts/freshDevelopmentGuard.mjs)`. It excludes
the protected tables and uses explicit table names; it does not use `TRUNCATE ... CASCADE`.

The plan must not be treated as authorization. A future live cleanup requires separate
approval, a fresh identity check, paused writers, a read-only inventory, a reviewed transaction,
foreign-key validation, and post-transaction verification. No live cleanup implementation is
enabled by the dry-run script.

## Fresh migration preflight

The migration runner's read-only mode is:

```powershell
node scripts/dev-link-challenges-migrate.mjs --fresh-development
```

It fails closed unless the server reports Development, the project and endpoint match, no
production identity is involved, all reviewed user-owned tables are empty, no unknown
public table exists, the pending table is absent, the three approved migrations and checksums
match, and no stale writer transaction is present.

Execution remains separately gated and does not perform cleanup:

```text
--fresh-development --execute --confirm-fresh-development
--confirm-branch br-weathered-hall-b3dn9bub
--confirm-not-default
--confirm-checksum 475bce9c7ddea4a
```

The runner still refuses Production and pins the migration SQL checksum. For this one-time
additive migration only, execution additionally requires the explicit
`--confirm-empty-development-no-backup` acknowledgment together with `--fresh-development`,
the empty-database preflight, branch identity confirmation, the non-default confirmation, and
the exact checksum. This is not a general backup bypass and must not be reused for
data-bearing migrations.

## Required approval sequence

1. Review the inventory and dry-run plan.
2. Explicitly approve irreversible Development data deletion.
3. Pause application writers and execute a separately reviewed cleanup transaction.
4. Verify all user-owned tables are empty and the migration journal/schema are unchanged.
5. Run the fresh-development migration preflight again.
6. Separately approve and execute the pending migration.
7. Verify the schema and generated Prisma client.
8. Create fresh web/Firebase test accounts through normal flows.
9. Test Android exchange and linking.
10. Configure and verify an independent backup outside the two Neon branches before any
    future data-bearing migration execution approval. The empty-development migration remains
    separately gated by explicit no-backup risk acceptance.

No approval stage should be combined with another.
